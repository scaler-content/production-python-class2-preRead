2. The big idea: can someone else run it?

Your Class 1 program works. But imagine you email just that one file to a colleague. They double-click it and see this:

FileNotFoundError: [Errno 2] No such file or directory: 'data/cases.csv'

Nothing is wrong with your rules. The program simply depends on things that exist only on your laptop. Programmers call this "works on my machine", and it is a joke for a good reason. A program is reproducible when someone else can follow written steps on their own machine and get the same result. That is the goal of Class 2.

Inside src/meridian_workbench/ your Class 1 file gets cut into small pieces. Each piece has one job, and a name that says what it is.

5. Your own Python: virtual environments and pip

The problem

Your computer has one Python installed. Every package you ever installed went into that one shared Python. Now picture three projects. One needs version 1 of a package, another needs version 2, and a colleague has a different set installed anyway. They cannot all live in one shared place.

The fix: a virtual environment

A virtual environment is a private copy of Python that belongs to one project. Packages you install go into the project, not into your whole computer. If something breaks, you delete the folder and rebuild it. It lives in a folder called .venv inside your project.

Picture it Each project gets its own toolbox on its own workbench. A shared toolbox that every project dips into ends up with the wrong tool at the wrong time.

Three ideas, three commands

IdeaWhat it meansCommand
CreateMake the private Python, once per projectpython -m venv .venv
ActivateTell this terminal to use it. Do this in every new terminalsee below
InstallFetch packages into it with pippython -m pip install …
Create (use py if python is not found), then activate
py -m venv .venv
.venv\Scripts\Activate.ps1
"Running scripts is disabled on this system" Windows blocks the activation script by default. Run this once, then try activating again: 
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
Create, then activate
python3 -m venv .venv
source .venv/bin/activate

When it works, the start of your prompt changes to (.venv). That is your signal. Everything you run in that terminal now uses the private Python. Type deactivate to leave.

learner@laptop:~/meridian-workbench$
(.venv)learner@laptop:~/meridian-workbench$

Top: before activation. Bottom: after. Look for the green (.venv) tag.

pip, and why we pin versions

pip fetches packages: code that other people wrote and shared. Write python -m pip rather than pip on its own, because that way you are sure it belongs to the Python you are using. A pinned version uses two equals signs and fixes the exact release.

python -m pip install python-dotenv==1.0.1

Without the number, pip installs the newest version on the day you run it. A colleague installing a month later may get something different, and a program that worked may quietly stop. Pinning is a promise that everyone gets the same thing.

Lists get long, so we write them in a file called requirements.txt, and install the whole list in one go. Class 2 also introduces pyproject.toml, the file that describes the project itself: its name, the Python it needs and the packages it depends on. You will read one together in class.

requirements.txt
-e .
python-dotenv==1.0.1
ruff==0.6.9
python -m pip install -r requirements.txt

The line -e . installs your own project in "editable" mode, so Python can find your code from anywhere and your edits take effect straight away. ruff is a checker that reads your code and spots small mistakes.

The most common mistake Forgetting to activate. If your prompt has no (.venv) and you run pip install, the package goes into your computer's global Python, not into the project. You will see this in the practice terminal below.

6. Settings, secrets and what Git must never see

Right now the batch date is written inside your code. If the ops lead wants a report as of the 13th, someone has to edit the program. And later, when you need a password or an API key, it must never end up in code. Every program knows three kinds of things:

Rules

Business logic the company has decided. A change needs a review and a test. Lives in code.

Example: DELIVERED and CANCELLED count as closed.

Settings

Values that change between runs or machines. Not secret. Live in a file.

Example: the batch date, the data folder.

Secrets

Anything that gives access to something. Never in code. Never in Git.

Example: an API key or password.

Click an item, then click the bin where it belongs.

Three files you will meet

config/settings.toml holds settings. It is not secret, so it is shared. TOML is just a settings format: square brackets name a section, and key = value lines sit inside.

config/settings.toml
[paths]
data_dir = "data"
output_dir = "outputs"

[rules]
batch_date = "2025-03-10"

Environment variables are named values that live in your terminal session. They can override the file for one run, without anyone editing a file. In class you will run the report for a different date this way.

.env is a local file for your own machine. It can hold real values, so it is never shared. Next to it sits .env.example: a template with no real values, which is shared, so a stranger can see which variables exist.

.env.example (shared, no real values)
# Copy this file to .env for local use. Never commit .env.
# MERIDIAN_BATCH_DATE=2025-03-10

# Placeholder for a later class. Not used yet.
MERIDIAN_LLM_API_KEY=

.gitignore: telling Git what to skip

Git tracks everything in a folder unless you say otherwise. A file called .gitignore lists what to skip, one pattern per line. A name ending in / is a folder.

.gitignore
# Virtual environment
.venv/

# Secrets and local settings
.env

# Generated files
outputs/

# Python caches and build files
__pycache__/
*.pyc
*.egg-info/
A secret in Git is a secret forever
  • A secret in code travels with every copy of the project and stays in the history. "The repository is private" is not a safe plan, because access changes.
  • .gitignore only stops files Git is not already tracking. If a key was ever committed, adding it to .gitignore later does nothing. Treat it as leaked and replace it.
  • In Class 2 there is no real secret anywhere. The key line is an empty placeholder. That is the safe way to practise.

For each file in the project, decide whether it goes into Git or stays out.

7. Git: four places a change travels

Until now, if you broke something your only tool was undo. Git remembers every saved version of your project, who changed what, and why. GitHub is a website that stores a copy online so other people can get it. Git is the tool. GitHub is the place.

Git works in four places. A change moves from left to right:

Working folderThe files you see and edit
→
StagingA waiting room for what goes in the next snapshot
→
Local historySaved snapshots on your computer
→
GitHubThe copy online, shared with others

The commands that move a change: git add (folder to staging), git commit (staging to history), git push (history to GitHub). Going the other way, git pull brings other people's changes into your folder.

Picture it A group photo. You choose who stands in the frame (git add), take the photo with a caption (git commit), and only then post it to the shared album (git push). Teammates download the album with git pull.

The commands you will use

What you wantCommandNotes
Start a repositorygit init -b mainCreates a hidden .git folder that holds the history. Once per project.
Ask what is going ongit statusYour best friend. Run it before and after everything.
Stage changesgit add .The dot means "everything here". Read the list afterwards.
Save a snapshotgit commit -m "message"The message is for the next person who reads the history.
See the historygit log --onelineOne line per snapshot.
Link to GitHubgit remote add origin URLSaves the online address under the short name origin.
Send to GitHubgit push -u origin main-u remembers the link, so later git push is enough.
Copy a project oncegit clone URLA full copy with history. Done once, by your partner.
Get new changesgit pullDone often.
The rhythm to remember Clone once, pull often. Commit, then push. And always run git status before you commit, to check that nothing secret is on the list.

Try it: your first commit

The practice terminal below starts inside the project folder. It contains a secret file (.env) and a virtual environment (.venv) on purpose. Your job is to commit the project without them. This pretend Git never contacts the internet.

  • Tell Git who you are: git config --global user.name "Your Name" and git config --global user.email "you@example.com"
  • Start the repository: git init -b main
  • Look: git status. Do you see .env and .venv/ in the list?
  • Ignore them. Write both into .gitignore: echo ".venv/" > .gitignore, then echo ".env" >> .gitignore
  • Stage everything safe: git add ., then check with git status
  • Save the snapshot: git commit -m "Create Workbench V0"
  • See it in the history: git log --oneline
  • Publish: git remote add origin https://github.com/your-username/meridian-workbench.git, then git push -u origin main
